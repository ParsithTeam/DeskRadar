# موارد باقی‌مانده و ناسازگاری‌های بک‌اند با فرانت

این فهرست فقط موارد موردنیاز فرانت را پوشش می‌دهد. بخش چت و بازخورد تحلیل در این سند نیست.

## موارد پیاده‌نشده

### ۱. احراز هویت و تشخیص نقش

- لاگین واقعی، توکن، دریافت کاربر جاری و تشخیص نقش `user` و `admin` وجود ندارد.
- لیست تیکت‌های کاربر با پارامتر `current_user` گرفته می‌شود و هر شخص می‌تواند نام کاربر دیگری را ارسال کند.
- مسیرهای ادمین و جزئیات تیکت کنترل دسترسی ندارند.

**انتظار فرانت:** کاربر و نقش او از توکن مشخص شود و هر کاربر فقط به اطلاعات مجاز خودش دسترسی داشته باشد.

### ۲. اتصال کامل به دیتابیس

- تیکت‌ها، رخدادها و هشدارها هنوز داخل لیست‌های موقت حافظه نگهداری می‌شوند.
- با ری‌استارت بک‌اند همه اطلاعات پاک می‌شود و این روش برای اجرای واقعی یا چند worker مناسب نیست.

**انتظار فرانت:** تمام اطلاعات از دیتابیس واقعی خوانده و در آن ذخیره شوند.

### ۳. تغییر وضعیت تیکت

- متد تغییر وضعیت در Repository وجود دارد، اما API قابل استفاده برای فرانت تعریف نشده است.

**انتظار فرانت:** یک API مانند `PATCH /api/tickets/{id}/status` با ورودی زیر وجود داشته باشد:

```json
{ "status": "in_progress" }
```

و تیکت به‌روزشده را برگرداند.

### ۴. پایگاه دانش

- فایل route پایگاه دانش خالی است و router آن نیز در برنامه ثبت نشده است.

**انتظار فرانت:** API لیست، جزئیات، ایجاد و ویرایش مقاله‌های پایگاه دانش پیاده‌سازی شود.

### ۵. تخصیص هشدار به ادمین

- هنگام خواندن هشدار فقط `is_read` تغییر می‌کند و ادمینی که هشدار را خوانده ثبت نمی‌شود.
- فیلدهای شناسه و نام ادمین مسئول در مدل پاسخ وجود ندارند.

**انتظار فرانت:** اولین ادمینی که هشدار را می‌خواند به‌صورت اتمیک مسئول آن شود؛ هشدار برای همه خوانده‌شده نمایش داده شود و `assigned_admin_id` و `assigned_admin_name` در خروجی برگردد. ادمین‌های بعدی نباید بتوانند مسئول را تغییر دهند.

### ۶. اتصال تحلیل به AI اصلی

- تحلیل فعلی کاملاً تستی و بر اساس چند کلمه ثابت است.
- متن پاسخ، دلیل‌ها و confidence به‌صورت ثابت و آزمایشی برگردانده می‌شوند.
- تا زمانی که AI اصلی متصل نشود، جریان واقعی تشخیص رخداد و ایجاد هشدار هم قابل اتکا نیست.

**انتظار فرانت:** تحلیل واقعی از سرویس AI گرفته و با ساختار ثابت و معتبر ذخیره شود.

## مواردی که مطابق انتظار کار نمی‌کنند

### ۱. API هشدارها خطای ۵۰۰ می‌دهد

- Repository شناسه هشدار را با نام `id` ذخیره می‌کند.
- Schema پاسخ فیلدی با نام `alert_id` می‌خواهد.
- در نتیجه وقتی هشدار وجود داشته باشد، اعتبارسنجی پاسخ شکست می‌خورد و گرفتن لیست یا خوانده‌کردن هشدار می‌تواند خطای ۵۰۰ بدهد.

**اصلاح موردنیاز:** نام فیلد شناسه در ذخیره‌سازی و Schema یکسان شود.

### ۲. تغییر وضعیت رخداد خراب است

- آدرس route به‌اشتباه `/incidents/{id}/satus` نوشته شده است.
- route متد `update_incident_status` را صدا می‌زند، ولی نام متد موجود در Service برابر `update_status` است.
- ثابت خطای ۴۰۰ نیز به‌اشتباه `Http_400` نوشته شده است.

**نتیجه:** تأیید، رد کردن (`dismissed`) و رفع رخداد از فرانت با خطا مواجه می‌شود.

**اصلاح موردنیاز:** مسیر به `/incidents/{id}/status` تغییر کند، نام متد یکسان شود و خطای ۴۰۰ از `HTTP_400_BAD_REQUEST` استفاده کند.

### ۳. خروجی لیست تیکت‌ها ناقص است

- لیست کاربر فقط شناسه، عنوان، زمان و وضعیت‌ها را برمی‌گرداند.
- لیست ادمین دسته‌بندی و درصد اطمینان تحلیل را برنمی‌گرداند.
- پاسخ لیست‌ها `total` ندارد و فقط آرایه برمی‌گرداند؛ بنابراین صفحه‌بندی درست برای بیش از ۱۰۰ تیکت ممکن نیست.
- فیلترهای موردنیاز فرانت مانند جستجو، دسته‌بندی و فوریت در API کامل نیستند.

**حداقل انتظار فرانت برای هر آیتم لیست ادمین:**

```text
ticket_id, title, requester, department, analysis_status,
ticket_status, created_at, urgency, category, confidence
```

پاسخ صفحه‌بندی‌شده نیز باید `items` و `total` داشته باشد. لازم نیست کل جزئیات تحلیل داخل لیست ارسال شود.

### ۴. جزئیات رخداد اطلاعات تیکت‌های مرتبط را ندارد

- خروجی رخداد فقط `matched_ticket_ids` و `ticket_count` را می‌دهد.
- عنوان تیکت‌های مرتبط و درصد شباهت آن‌ها برگردانده نمی‌شود.
- دسته‌بندی رخداد نیز در خروجی وجود ندارد.

**انتظار فرانت:** جزئیات رخداد آرایه‌ای مانند زیر داشته باشد:

```json
{
  "tickets": [
    { "ticket_id": 123, "title": "عنوان تیکت", "similarity": 0.91 }
  ]
}
```

### ۵. خروجی تحلیل تیکت ناقص و بعضی مقادیر نامعتبر است

- مقدار فوریت در یکی از حالت‌ها `mediume` برگردانده می‌شود که مقدار معتبری نیست.
- تیکت‌های مشابه در پاسخ جزئیات تیکت قرار نمی‌گیرند.
- مقاله مرتبط فقط شناسه و عنوان دارد و امتیاز تطابق آن در Schema خروجی نیست.

**انتظار فرانت:** فوریت یکی از `low`, `medium`, `high`, `critical` باشد و تحلیل، تیکت‌های مشابه و مقاله مرتبط را همراه امتیاز تطابق برگرداند.

### ۶. پاسخ اجرای دستی تحلیل استاندارد نیست

- در پاسخ `POST /api/tickets/{id}/analyze` شناسه تیکت به‌اشتباه به‌عنوان کلید عددی دیکشنری قرار گرفته است.

**انتظار فرانت:** پاسخ `202` ساختار مشخص زیر را داشته باشد:

```json
{ "ticket_id": 123, "analysis_status": "pending" }
```

### ۷. نوع هشدار اضافی و ناهماهنگ وجود دارد

- نوع `SAL_RISK` در بک‌اند باقی مانده است که هم نام آن اشتباه است و هم طبق تصمیم فعلی پروژه هشدار SLA/System نباید وجود داشته باشد.

**انتظار فرانت:** فقط هشدارهای مربوط به رخداد و تیکت فوری نگه داشته شوند.
